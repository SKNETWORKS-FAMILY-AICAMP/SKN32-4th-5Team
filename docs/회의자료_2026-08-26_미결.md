## 3. ① 계정 모델 — 쉽게

### 3.1 지금 무슨 일이 벌어지고 있나

우리 DB 에 `pets`(반려동물) 라는 표가 있고, 거기에 **"이 아이의 주인은 누구인가"** 칸이 있다.
그런데 그 칸에 주인을 적는 방식이 **두 벌**이다.

```
3차 방식 (FastAPI · SQLAlchemy)
    주인 =  "a3f4b2c1-9d8e-4f7a-b6c5-1e2d3c4b5a69"     ← 긴 글자
4차 방식 (Django)
    주인 =  1                                            ← 숫자
```

사물함 하나에 **한 사람은 이름표를 붙이고 다른 사람은 번호 스티커를 붙이는** 상황이다.
사물함은 하나인데 붙이는 규칙이 둘이라, 둘 다 자기 규칙대로 정리하려 하면 부딪힌다.

**그 부딪힘이 지금 실제로 일어나고 있다.**

```powershell
python manage.py migrate        # ← 끝까지 못 돈다
```

그래서 셋업 메모가 *"전체 migrate 는 pets/diary 스키마 충돌 나므로 위 4개만"* 이라고
우회하고 있다. 즉 **`pets` 와 `diary` 의 표 만들기가 아직 한 번도 실행되지 않았다.**

### 3.2 왜 하필 지금 정해야 하나

Django 에는 규칙이 하나 있다.

> **"사용자를 어떻게 표현할지는 프로젝트를 시작할 때 정하라."**

Django 가 사용자 표를 한 번 만들고 나면, 그 표에 다른 모든 표가 연결된다.
나중에 사용자 표현 방식을 바꾸려면 **연결된 표를 전부 다시 짜야 한다.**
Django 공식 문서도 이것을 경고한다.

지금 우리는 운이 좋다.

```
pets/0001 · pets/0002 · diary/0001   ← 아직 한 번도 적용된 적이 없다
```

**표가 아직 안 만들어졌으니 지금 바꾸는 비용은 거의 0 이다.**
누군가 한 번 `migrate` 를 끝까지 돌리는 순간부터 비싸진다.

### 3.3 🔴 "3차 데이터를 버린다"가 무슨 뜻인지 — 오해 방지

이 결정에서 **버릴 수도 있는 것은 아주 좁은 범위**다. 헷갈리기 쉬우니 명확히 한다.

| | 무엇 | 이번 결정과 |
|---|---|---|
| 🗑 **버릴 수 있는 것** | MySQL 의 **가상 계정 · 가상 펫 · 가상 다이어리 기록** | 관계 있음 |
| ✅ **그대로 남는 것** | 근거 문서 **888청크**(Chroma 벡터DB) | **무관** |
| ✅ | 사실 표 888행 · 45출처 · 규칙 테이블 | **무관** |
| ✅ | 골든셋 60건 · 0단계 기준선 · 평가 하네스 | **무관** |
| ✅ | 판정 로직 · 단위 테스트 589건 | **무관** |

**즉 "3차 데이터"라고 부르는 것 중 프로젝트의 핵심 자산은 이 결정과 아무 상관이 없다.**
걸려 있는 것은 **계정 로그인 정보와 시연용 펫·기록**뿐이다.

그리고 그것들은 **처음부터 가상이었다.**

> `archive-3rd/01_데이터-수집및전처리.md` §13 — *"내부 데이터 설계 (가상 프로필·기록)"*
> `archive-3rd/00_기획-요구사항분석.md` — WS1 *"가상 프로필·기록 생성"*

실제 사용자의 데이터가 아니라 **시연을 위해 우리가 만들어 넣은 것**이다.
다시 만드는 데 드는 비용은 스크립트 한 번이다.

### 3.4 두 선택지

| | **A. Django 기본 User (숫자)** | **B. 커스텀 User (글자)** |
|---|---|---|
| 하는 일 | 지금 코드 그대로 둔다 | `accounts/` 에 사용자 모델을 새로 정의 |
| 3차 가상 데이터 | **버리고 새로 만든다** | 옮길 수 있다 |
| 작업량 | **없음** (이미 이 상태) | 지금 하면 작다 · **나중엔 크다** |
| 위험 | 없음 | 지금 안 하면 되돌리기 비쌈 |
| 얻는 것 | 단순함 · Django 관리자와 바로 맞음 | 3차 스키마와 1:1 |

### 3.5 권고 — **A**

이유는 셋이다.

1. **옮길 데이터가 시연용 가상 데이터다.** 지키려는 대상이 사실상 없다
2. **B 의 이득이 4차 요구사항에 없다.** 3차 스키마와 1:1 로 맞아서 좋은 점이
   4차 산출물 어디에도 필요하지 않다
3. **A 는 이미 그 상태다.** 아무것도 안 하면 A 로 간다 — 다만 **"안 해서 그렇게 된 것"과
   "정해서 그렇게 한 것"은 다르다.** 정하고 기록해야 다음 사람이 흔들리지 않는다

> ⚠️ **결정하지 않는 것도 결정이다.** 누군가 `migrate` 를 끝까지 돌리면 그 순간 A 로 굳는다.
> 그때는 우리가 고른 게 아니라 **그냥 그렇게 된 것**이 된다.

### 3.6 A 로 가면 그다음에 할 일

1. `accounts/models.py` 는 비워 둔다 (기본 `auth.User` 사용) — 지금 그대로
2. FastAPI 의 `auth` · `users` · `pets` · `records` 라우터와 SQLAlchemy 모델을 **폐기**한다
3. DB 를 하나로 합친다 (`DJANGO_DATABASE_URL` 과 `DATABASE_URL` 분리를 없앤다)
4. `python manage.py migrate` 가 **깨끗한 DB 에서 끝까지 도는지** 테스트로 고정한다 (`13 §5.2` 1번)
5. 시연용 가상 데이터를 만드는 스크립트를 하나 둔다

2번이 통합 테스트 63건을 깨뜨리는데, **그것은 7b 단계가 어차피 재작성할 것들**이다.

그 방식이 안 맞는다.
