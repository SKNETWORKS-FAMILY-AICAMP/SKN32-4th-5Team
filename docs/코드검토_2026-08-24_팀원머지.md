## 2. 🔴 결정 ① — `pets` · `diary_entries` 의 소유권

### 무엇이 있나

```
Django      pets.Pet(db_table="pets", managed=True)              ← 마이그레이션이 소유
SQLAlchemy  Pet(__tablename__="pets")                            ← create_all 이 소유
Django      diary.DiaryEntry(db_table="diary_entries", managed=True)
SQLAlchemy  DiaryEntry(__tablename__="diary_entries")
```

같은 이름의 테이블을 두 ORM 이 각자 소유한다고 믿는다. 컬럼도 다르다 —
Django 쪽 `user` FK 는 `auth.User`(**정수 PK**)를 가리키고, SQLAlchemy `User.user_id` 는
**문자열 UUID** 다.

### 지금 어떻게 돌고 있나 — **문서 두 개가 다른 말을 한다**

| 출처 | 말하는 것 |
|---|---|
| `.env.example` | *"Django 전용 DB. **DATABASE_URL 과 일부러 다른 파일을 쓴다** — 같은 파일을 공유하면 스키마가 깨진다"* |
| `docs/lgj/01_체크해야될사항들.md` | `DJANGO_DATABASE_URL` 과 `DATABASE_URL` 을 **같은 MySQL** 로 지정 |

**메모대로 하면 깨진다.** 그래서 같은 메모가 *"전체 `migrate` 는 pets/diary 스키마 충돌
나므로 위 4개만"* 이라고 우회하고 있다. 즉 **`pets/0001` · `pets/0002` · `diary/0001` 은
아직 한 번도 적용된 적이 없다.** `0002` 가 넣는 `age` · `gender` · `photo` 컬럼이
실제 테이블에 있는지 없는지 지금 아무도 모른다.

### 끝 그림은 이미 정해져 있다

`auth` · `users` · `pets` · `records` 가 전부 Django 로 가면
**FastAPI 는 DB 가 필요 없어진다** — 잔류 라우트 `ask` · `meta` · `internal_report`
셋 다 DB 를 안 쓴다. 14 §2.1 의 *"`database.py` → Django, `init_db.py` → 삭제"* 가 그 뜻이다.

| 안 | 방식 | 대가 |
|---|---|---|
| **A** (권장) | **Django 가 소유한다.** FastAPI 의 `auth`·`users`·`pets`·`records` 라우터와 SQLAlchemy 모델을 **폐기**한다. DB 는 하나 | 통합 테스트 63건이 그 시점에 깨진다 — 그런데 그건 **7b단계가 어차피 재작성할 것들**이다 |
| B | 두 DB 를 계속 분리해 둔다 (현재 `.env.example` 의 상태) | 같은 사람이 Django 에서 등록한 펫이 FastAPI 쪽에 안 보인다. **데이터가 둘로 갈린 채 시연하게 된다** |
| C | 하나의 DB 를 두 ORM 이 공유하고 Django 를 `managed=False` 로 | 마이그레이션을 누가 하나. `chat` 은 읽기만 해서 되지만 `pets`·`diary` 는 **쓴다** |

**A 를 권한다.** B 는 지금만 편하고 시연에서 드러난다. C 는 쓰기가 있는 테이블에는 안 맞는다.

**언제 하나 —** 7b단계(통합 63건 재작성)와 같은 작업이다. 따로 잡지 말고 묶는다.

## 3. 🔴 결정 ② — 커스텀 User 모델 (시한이 있다)

`accounts/models.py` 는 비어 있고 `AUTH_USER_MODEL` 설정도 없다.
`accounts/views.py` 는 `django.contrib.auth.models.User` 를 직접 쓴다 — **정수 PK** 다.

`pets/models.py` 와 `diary/models.py` 의 머리말이 스스로 경고해 뒀다.

> ⚠️ 계정 앱이 아직 없어서 임시로 기본 User 를 쓴 것이고,
> 계정 앱이 정해지면 이 FK 를 다시 봐야 한다.

그 사이 계정 앱(`a2f761d`)이 들어왔고, **"임시"가 아무도 결정하지 않은 채 굳어가고 있다.**

🔴 **Django 는 커스텀 User 모델을 첫 마이그레이션 이후에 바꾸는 것이 극히 어렵다.**
pets/diary 마이그레이션이 아직 적용 안 된 지금이 **값싸게 정할 수 있는 마지막 구간**이다.

| 안 | 방식 | 대가 |
|---|---|---|
| **A** | Django 기본 `auth.User`(정수 PK)를 쓴다 | SQLAlchemy `users` 테이블과 문자열 UUID 를 버린다. 3차 데이터는 시연용이라 버려도 된다. `deps.get_current_user_id` 가 `str` 을 반환하던 계약은 Django 쪽에서 새로 정의된다 |
| B | `accounts/` 에 문자열 PK 커스텀 User 를 만든다 | 원본 스키마와 1:1 로 맞는다. **지금 아니면 못 한다.** 작업량은 지금 시점에선 작다 |

결정에 필요한 질문 하나 — **3차 DB 의 기존 계정·기록을 4차로 넘길 것인가.**
넘긴다면 B, 새로 시작한다면 A 가 단순하다.

## 4. 이 검토에서 고친 것

| 파일 | 무엇을 |
|---|---|
| `pyproject.toml` · `constraints.txt` | `python-dotenv` 를 **핵심 의존성**으로 선언 + 핀 |
| `webapp/settings.py` | `DEBUG` 기본값 `true` → **`false`** |
| `webapp/settings.py` · `.env.example` | `INFERENCE_INTERNAL_URL` **8000 → 8001** |
| `.env.example` | `DJANGO_DEBUG` · `DJANGO_ALLOWED_HOSTS` 추가 |

**`python-dotenv` 가 왜 핵심인가.** `app/routes/__init__.py` 최상단이
`from dotenv import load_dotenv` 를 부른다 — **상시 임포트 경로다.**
지금 초록인 것은 venv 에 우연히 깔려 있어서고, 새 환경에서 `.[api]` 만 깔면
앱이 통째로 임포트 실패한다. 하필 **그 파일 자신의 머리말**이
*"의존성이 늘어난 모듈은 분류가 바뀐 것이다"* (D-70)라고 적어 둔 자리다.

**`INFERENCE_INTERNAL_URL` 이 왜 버그인가.** 8000 은 **Django 자기 포트**다.
그 값이면 `GET /api/report` 가 자기 자신에게 요약을 요청한다.
nginx 의 `upstream fastapi` 는 8001 이고 설치 메모도 `uvicorn --port 8001` 이다.

## 6. 두 인증 체계가 동시에 열려 있다

nginx 가 `/api/records` · `/api/report` 만 Django 로 보내고 **나머지 `/api/*` 는 FastAPI** 로 보낸다.
`DATABASE_URL` 이 있는 환경에서는 FastAPI 의 `auth`·`pets`·`users` 라우터가 로드되므로:

```
POST /accounts/login/    → Django 세션 인증   (ksr, a2f761d)
POST /api/auth/login     → FastAPI JWT 인증   (3차, 여전히 살아 있음)
```

이행 중이라 자연스러운 상태이고 지금 당장 위험하지는 않다 —
다만 **언제 FastAPI 쪽을 닫을지**가 정해져 있어야 한다. §2 A안과 같은 시점이다.
